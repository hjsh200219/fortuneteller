# 사주 상담 드라마투르기 프롬프트 설계

작성일: 2026-07-18

## 1. 배경

`fortuneteller`는 정확한 사주 계산 결과를 MCP 도구의 JSON으로 제공하지만, 사용자와 나누는 실제 대화의 연출은 MCP 클라이언트에 맡긴다. 현재 도구 설명에는 필수 정보 수집과 6항목 해석 구조만 있으며, 상담 전체의 긴장·호흡·반전을 일관되게 지휘하는 계약은 없다.

이 기능은 `F:/Project/out`의 드라마투르기 8원리를 사주 상담에 맞게 번역한다. 계산 로직을 서사 엔진으로 바꾸는 것이 아니라, MCP 서버가 클라이언트에 제공하는 프롬프트 계약으로 정보 수집부터 결과 해석까지의 공연 방식을 정한다.

## 2. 확정된 제품 결정

- 적용 범위: 일반 사주, 운세, 궁합의 정보 수집부터 결과 해석까지
- 제외 범위: 달력 변환, 설정 관리 등 유틸리티 응답
- 기본 톤: 절제된 상담극
- 공개 방식: 한 번에 전체를 나열하지 않고 비트별로 단계적 공개
- 사용자 중심축: "지금 가장 궁금한 한 가지"를 선택 입력으로 수집
- 최우선 경험: 통찰이나 행동 지침보다 몰입과 재미
- 호환성: 응답 구조 변경이 허용되지만, 선택한 프롬프트 중심 접근에는 불필요하므로 계산 JSON은 유지
- 구현 방식: 상태형 세션이나 서버 렌더링이 아닌 MCP 프롬프트 중심 연출

## 3. 목표와 비목표

### 목표

1. 지원 MCP 클라이언트가 별도 사용자 설정 없이 드라마투르기 지침을 받을 수 있게 한다.
2. 정보 수집, 첫 공개, 긴장, 반전, 후속 선택에 일관된 대화 호흡을 부여한다.
3. 모든 극적 표현을 도구 결과의 사실에 묶어 환각과 운명론적 단정을 막는다.
4. 자동화 가능한 계약 테스트와 대표 대화 시나리오로 회귀를 감지한다.
5. 기존 10단계 사주 계산 파이프라인과 도구 결과를 변경하지 않는다.

### 비목표

- 서버가 완성된 상담 문장을 생성하지 않는다.
- 상담 세션, 현재 막, 사용자 선택을 서버에 저장하지 않는다.
- 외부 LLM 또는 외부 API 의존성을 추가하지 않는다.
- 계산 데이터에 없는 사건이나 심리를 추론하는 기능을 추가하지 않는다.
- 모든 MCP 클라이언트에서 연출 준수를 강제하지 않는다.
- 달력 변환과 설정 관리에 극적 표현을 넣지 않는다.

## 4. 아키텍처

### 4.1 단일 정본

`src/core/dramaturgy-prompt.ts`를 드라마투르기 계약의 단일 정본으로 둔다. 이 모듈은 다음을 제공한다.

- 8개 원리의 구조화된 상수
- 사실성·안전·오류 처리 규칙
- 지원 도구와 제외 도구 범위
- 자동 서버 지침 문자열
- 선택형 MCP prompt 응답을 만드는 함수

구조화된 원리 목록으로부터 최종 텍스트를 조립해, 규칙 누락과 중복을 단위 테스트로 검증할 수 있게 한다. 계산 모듈이나 데이터 레이어에는 의존하지 않는다.

### 4.2 자동 서버 지침

`createMCPServer()`가 SDK `ServerOptions.instructions`에 드라마투르기 계약을 전달한다. 서버 초기화 지침은 다음 역할을 한다.

- 지원 상담 도구를 호출하기 전 필수 사용자 정보를 확인한다.
- 현재 고민을 선택적으로 한 가지 묻는다.
- 도구 결과를 한 번에 덤프하지 않고 비트별로 공개한다.
- 사실성·안전·오류 처리 규칙을 상담 전체에 적용한다.
- 유틸리티 도구는 간결하고 직접적으로 답한다.

### 4.3 선택형 MCP prompt

서버 capability에 `prompts`를 추가하고 다음 prompt를 노출한다.

- 이름: `dramatic_saju_consultation`
- 설명: 사실 기반 사주 상담을 절제된 상담극으로 진행하는 프롬프트
- 선택 인자: `focus` — 사용자가 현재 가장 궁금해하는 한 가지

`ListPromptsRequestSchema`는 prompt 메타데이터를 반환하고, `GetPromptRequestSchema`는 동일한 단일 정본에서 만든 메시지를 반환한다. `focus`가 없으면 일반 상담으로 진행한다. 이 prompt는 자동 서버 지침을 보완하는 명시적 진입점이며 서로 다른 규칙을 복제하지 않는다.

### 4.4 도구 설명 연결

다음 도구 설명에는 `dramatic_saju_consultation` 계약을 따르라는 짧은 문구를 추가한다.

- `analyze_saju`
- `check_compatibility`
- `get_daily_fortune`
- `get_dae_un`
- `get_fortune_by_period`

다음 도구는 연결하지 않는다.

- `convert_calendar`
- `manage_settings`

도구 설명은 세부 규칙을 복사하지 않는다. 세부 규칙의 정본은 `dramaturgy-prompt.ts` 하나뿐이다.

## 5. 대화 흐름

### 5.1 문턱

상담 도구 호출 전 기존 필수 항목을 확인한다.

- 이름
- 양력/음력
- 생년월일시 (`YYYY-MM-DD HH:mm`)
- 성별
- 출생지 시군구
- 음력일 때 윤달 여부

이어 "지금 가장 궁금한 한 가지"를 선택적으로 묻는다. 사용자가 답하지 않거나 일반 해석을 원하면 진행을 막지 않는다. 필수 정보를 여러 턴에 걸쳐 연극적으로 끌지 않고, 누락 항목을 한 번에 간결하게 요청한다.

### 5.2 예고

도구 호출 전에는 "가장 강한 징후부터 차례로 보겠다"처럼 진행 방식만 예고한다. 도구 결과를 받은 뒤에는 이번 상담에서 실제로 확인된 갈등축을 한 문장으로 예고한다. 계산되지 않은 사실이나 결과를 호출 전에 암시하지 않는다.

### 5.3 첫 징후

도구 결과에서 가장 설명력이 높은 근거 하나만 먼저 제시한다. 근거는 오행, 십성, 일간, 격국, 용신, 운의 흐름 등 반환 필드에 직접 연결한다. 긴 JSON이나 6항목 해석 전체를 한 번에 보여주지 않는다.

### 5.4 균열

서로 다른 방향을 가리키는 두 근거를 맞세운다. 예를 들어 강한 기운과 약한 기운, 타고난 성향과 현재 운의 요구처럼 실제 결과에서 확인되는 대비만 사용한다. 이 지점에서 사용자의 반응 또는 더 보고 싶은 영역을 묻는다.

### 5.5 반전

앞에서 약점처럼 보인 요소가 조건에 따라 어떻게 자원으로 작용하는지, 또는 강점이 어느 상황에서 부담으로 바뀌는지 재구성한다. 반전은 새 사실의 창작이 아니라 기존 근거의 관점 전환이어야 한다.

### 5.6 선택의 문

다음에 볼 영역을 2~3개 제시한다. 사용자가 전체 공개를 요청하면 단계적 공개를 강제하지 않고 한 응답 안에서 남은 내용을 정리한다.

## 6. 드라마투르기 8원리의 채팅 번역

| # | 원리 | 사주 상담 적용 |
|---|------|----------------|
| 1 | 대사는 행동 | 각 턴은 호기심 유발, 긴장 고조, 관점 전환, 선택 요청 중 하나의 목적만 가진다. |
| 2 | 서브텍스트 | 설명을 반복하지 않고 상반된 근거와 함의로 의미를 만든다. |
| 3 | 방백 | 숨겨진 추론이나 chain-of-thought가 아닌, 결과에 근거한 짧은 상징적 문장만 사용한다. |
| 4 | 지위 시소 | 사용자를 낮추지 않는다. 상반된 기운이나 시기 조건 사이에서 무엇이 우세한지를 이동시킨다. |
| 5 | 극적 아이러니 | 뒤에서 회수할 근거를 앞에서 공정하게 예고한다. 계산되지 않은 비밀을 꾸며내지 않는다. |
| 6 | 침묵 | 가짜 타이핑 지연 없이 짧은 문장, 줄바꿈, 제한적인 말줄임표로 호흡을 만든다. |
| 7 | 공간 | 넓은 인생 흐름에서 사용자의 현재 고민으로 서술 초점을 좁힌다. |
| 8 | 노출의 갈등화 | 데이터 목록 대신 서로 다른 방향을 가리키는 실제 근거를 맞세운다. |

### 6.1 절제된 상담극의 문체 한계

- 기본은 자연스러운 한국어 존댓말이며, 이름을 확인했다면 필요한 순간에만 호칭으로 사용한다.
- `1막`, `[방백]`, 무대 지문 같은 표시는 사용자가 요청하지 않는 한 직접 노출하지 않는다.
- 한 비트에는 상징적 비유 또는 방백을 최대 하나만 사용한다.
- 한 비트의 핵심 질문은 하나만 두고, 말줄임표를 반복해 긴장을 과장하지 않는다.
- 전문 용어를 사용할 때는 반환 데이터와 연결하고 일상 언어로 바로 풀이한다.
- 원시 JSON이나 내부 필드명을 그대로 덤프하지 않는다. 사용자가 근거 데이터를 요청하면 별도 표나 목록으로 제공한다.
- 무속인 흉내, 고어체, 과도한 예언자 어조 대신 차분한 해석자가 장면을 이끄는 느낌을 유지한다.

## 7. 사실성·안전 계약

1. 모든 핵심 해석은 도구가 반환한 필드 하나 이상에 직접 근거한다.
2. 반환 결과에 없는 과거 사건, 타인의 감정, 숨겨진 동기를 맞힌 척하지 않는다.
3. 예언은 확정형이 아니라 조건과 경향으로 표현한다.
4. 죽음, 질병, 파산, 이별 같은 공포를 클리프행어나 재방문 유도 수단으로 사용하지 않는다.
5. 사주 해석이 의료, 재정, 법률 결정을 대신한다고 표현하지 않는다.
6. 재미를 위해 공개 순서를 조절할 수 있지만, 같은 상담 흐름 안에서 예고한 내용을 회수한다.
7. 사용자가 불안을 보이면 긴장 연출을 낮추고 사실과 선택지를 직접적으로 설명한다.
8. 사용자 요청이 명확하면 드라마틱한 형식보다 요청한 길이와 형식을 우선한다.

## 8. 오류 처리

- 필수 입력 누락: 누락 항목과 올바른 입력 형식을 한국어로 안내한다.
- 잘못된 날짜·시간: 연출을 중단하고 `YYYY-MM-DD`, `HH:mm` 형식을 보여준다.
- 출생지 불명: 서울값을 조용히 가정하지 않고 기본값 적용 여부를 사용자에게 알린다.
- 도구 실패: 신비한 징조나 해석 불가의 운명처럼 포장하지 않고 기술적 실패임을 밝힌다.
- 근거 부족: 결론을 만들지 않고 필요한 분석 도구 또는 추가 정보를 안내한다.
- 유틸리티 도구: 오류 여부와 관계없이 극적 표현 없이 직접 답한다.

## 9. 데이터 흐름

```text
MCP 연결
  -> 서버 instructions 자동 제공
  -> 클라이언트가 필수 정보 + 선택 focus 수집
  -> 관련 계산 도구 호출
  -> 서버가 기존 JSON 사실 데이터 반환
  -> 클라이언트가 첫 징후 한 개 공개
  -> 사용자의 반응 또는 영역 선택
  -> 균열 -> 반전 -> 선택의 문 순으로 후속 해석
```

새 날짜, 새 인물, 새 분석 영역이 아니면 기존 도구 결과를 재사용한다. 서버는 상담 진행 상태를 저장하지 않는다. 대화 맥락을 유지하지 못하는 클라이언트에서는 단계적 공개의 품질이 낮아질 수 있으며, 이는 프롬프트 중심 접근의 의도된 한계다.

## 10. 테스트 전략

모든 구현은 TDD의 Red-Green-Refactor 순서로 진행한다.

### 10.1 단위 테스트

- 원리 목록이 정확히 8개이며 식별자가 중복되지 않는다.
- 생성된 자동 지침에 정보 수집, 단계적 공개, 사실성, 안전, 오류 처리 규칙이 포함된다.
- `focus`가 있을 때 prompt 메시지에 포함되고, 없을 때 일반 상담으로 구성된다.
- 지원 도구와 제외 도구 목록이 겹치지 않는다.

### 10.2 MCP 통합 테스트

- 서버 초기화 결과에 `instructions`가 존재한다.
- 서버 capability에 `prompts`가 선언된다.
- prompt 목록에서 `dramatic_saju_consultation`을 찾을 수 있다.
- prompt 조회가 유효한 MCP `PromptMessage`를 반환한다.
- 지원 도구 설명만 드라마투르기 계약을 참조한다.
- 기존 도구 호출 결과의 계산 데이터가 바뀌지 않는다.

### 10.3 대표 대화 시나리오

외부 LLM이나 API를 테스트에 추가하지 않는다. 대신 다음 시나리오를 프롬프트 계약의 수용 기준으로 고정한다.

- 일반 사주: 한 근거만 먼저 공개하고 다음 관심사를 질문한다.
- 궁합: 두 사람을 대칭적으로 다루며 갈등과 반전을 구성한다.
- 일일 운세: 짧은 도입 후 후속 영역을 선택하게 한다.
- 잘못된 시간 입력: 극적 표현 없이 `HH:mm` 형식을 안내한다.
- 달력 변환: 간결한 유틸리티 응답을 유지한다.

실제 문장 품질은 비결정적인 클라이언트 LLM에 달려 있으므로, 자동 테스트는 프롬프트와 배선의 계약을 검증하고 대표 시나리오는 사람이 읽을 수 있는 수용 기준으로 사용한다.

## 11. 완료 조건

- 승인된 대화 흐름과 8원리가 단일 프롬프트 정본에 반영된다.
- 자동 `instructions`와 선택형 MCP prompt가 같은 정본을 사용한다.
- 지원 도구와 유틸리티 도구의 연출 경계가 지켜진다.
- 10단계 사주 계산 파이프라인과 기존 JSON 결과가 변하지 않는다.
- 신규 테스트와 기존 테스트가 모두 통과한다.
- `npm test`, `npm run lint`, `npm run build`가 오류 없이 완료된다.

## 12. 알려진 한계

- MCP 클라이언트가 서버 `instructions`, prompt, 도구 설명을 모두 무시하면 연출을 강제할 수 없다.
- 프롬프트 중심 접근은 클라이언트 모델에 따라 문체와 호흡이 달라질 수 있다.
- 서버가 상태를 저장하지 않으므로 클라이언트가 대화 맥락을 잃으면 비트 진행도 함께 잃는다.
- 이 설계는 몰입과 재미를 우선하지만, 공포 유도와 사실 왜곡은 허용하지 않는다.
